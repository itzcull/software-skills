# Shipping procedure exercise

## Authority and scope

Skill baseline: f309ede22a1afbcfd05d7a0639a09bea8af741f4 (PR #14).
This is direct execution by the same assistant that edited the guidance. No independent reviewer, fresh agent context, or live user approval is simulated as genuine.

Only temporary repositories under this exercise directory may be changed. Commits and pushes are authorized solely to the fixture's local bare remote. No network remote, deployment, or real application is in scope.

The fixture controller supplies scripted product decisions. The executor may implement their bounded implications but may not silently choose an unspecified discount basis, waive a failed check, or call a candidate released. Scripted decisions are exercise inputs, not live stakeholder approvals.

The existing code is a flat 500-cent delivery charge, with public quote and checkout interfaces. Inputs are nonnegative integer cents; any discount is within the subtotal. Invalid inputs, taxes, persistence, security and production operations are excluded. This narrow scope does not claim product readiness.

## Loops and concern placement

- Feature loop: select the next criterion, receive cycle evidence, run all unit and CLI checks, review the candidate, then accept the fixture increment or return a blocker. The controller owns changes to requirements.
- Behavior loop: invoke the TDD RED, GREEN and REFACTOR phase instructions sequentially in this context. Persist and consume their handoffs. This does not test spawned-context orchestration or live guided-pairing approval.
- Related branch integration: the sync case integrates fixture trunk into its own checkout. Passing all tests is an inherited pre-push condition. Clean Git integration is not acceptance.

Currency units and backward compatibility are inherited concerns. Unit tests verify shipping decisions through shippingCharge; CLI tests verify the amount adapter and public output together. CLI checks are due before a commit or push, not deferred to CI. The quote function and CLI are public interfaces customers actually consume, so assertions remain independent of internal decomposition.

## Completion boundaries

A behavior cycle requires expected RED evidence, passing GREEN, explicit refactoring assessment and a cycle report. Feature acceptance additionally requires the complete test suite, a scoped review and disposition of outstanding questions. A failed inherited check blocks push and verified completion. No fixture acceptance authorizes release.

## Scripted cases

1. Normal: introduce free shipping at subtotals of at least 5000 cents.
2. Ambiguity: extend checkout with a discount, initially without specifying whether shipping eligibility uses gross or net subtotal. Stop without editing until the controller supplies a decision.
3. Failed verification: a controller-owned upstream parser change passes the old flat-fee checkout tests, but changes units from cents to whole currency units. Integrate it without a textual conflict and evaluate inherited checks. Do not push if they fail.
4. Changed requirement: independently from the blocked sync case, revise the accepted threshold from 5000 to 7500 cents. Preserve superseded requirements, obtain new RED evidence and evaluate the revised candidate.

Only the selected composition is exercised: structured-development, test-design, TDD phase execution, Git conventions, code review, and sync-branch. Not all 16 supporting skills are exercised.
